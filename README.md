# G4Z CUP

Сайт сообщества G4Z CUP и турниров по Dota 2, CS2 и другим дисциплинам:
расписание, группы, плей-офф, составы, итоги и админка для ведения матчей.

Главная постоянно показывает сообщество, активные турниры и недавние итоги.
`is_current` выделяет основной кубок. Каждый сезон остаётся доступен по
адресу `/t/<slug>`, новый кубок не затирает предыдущий.

---

## Стек

| Что        | Чем                                                     | Почему                                                          |
| ---------- | ------------------------------------------------------- | --------------------------------------------------------------- |
| Приложение | Next.js 16 (App Router) + React 19                      | серверные компоненты, server actions                            |
| Кэш        | Cache Components (`use cache`, `cacheTag`, `updateTag`) | страницы отдаются из предрендера, а не из базы на каждый запрос |
| База       | Supabase (Postgres)                                     | схема, вьюхи, триггеры и RLS — в миграциях репозитория          |
| Стили      | Tailwind 4                                              | токены темы в `app/globals.css`                                 |
| Тесты      | Vitest + Playwright + SQL-ассерты                       | логика сеток, авторизация, смоук страниц, триггеры БД           |
| Хостинг    | Vercel                                                  | preview-деплой на каждый PR                                     |

## Быстрый старт

Используйте Node.js 22 (`nvm use`): эта версия задана для локального окружения,
Vercel и CI.

```bash
npm install
cp .env.example .env.local     # заполнить значения, см. ниже
npm run dev                    # http://localhost:3000
```

### Переменные окружения

```bash
npm run secret                 # выведет строку AUTH_SECRET
npm run hash-password          # спросит пароль и выведет ADMIN_PASSWORD_HASH
```

| Переменная                      | Обязательна | Назначение                                                               |
| ------------------------------- | ----------- | ------------------------------------------------------------------------ |
| `NEXT_PUBLIC_SUPABASE_URL`      | да          | адрес проекта Supabase                                                   |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | да          | публичный ключ, RLS даёт ему только чтение                               |
| `SUPABASE_SERVICE_ROLE_KEY`     | да          | ключ записи, **только серверный**, никогда не с префиксом `NEXT_PUBLIC_` |
| `ADMIN_PASSWORD_HASH`           | да          | scrypt-хэш пароля организаторов                                          |
| `AUTH_SECRET`                   | да          | подпись cookie сессии (HMAC-SHA256), минимум 32 символа                  |
| `NEXT_PUBLIC_SITE_URL`          | нет         | канонический адрес для метаданных и sitemap                              |

Без ключей Supabase сайт собирается и запускается — просто без данных. Это нужно,
чтобы CI мог собрать приложение без секретов.

- `migrations/0008_stage_window.sql` — даты этапа и полоса стыковых матчей

- `migrations/0013_registration_commands.sql` — транзакционные операции и снимки составов

- `tests/logic.sql` — ассерты на триггеры и вьюхи

### Релиз 2: подготовка регистрации

Начата основа релиза: состав редактируется по ID, перестановка сохраняет связи
с драфтами/наградами, устаревшая вкладка не перезаписывает свежий состав.
Пустой ник удаляет игрока; новый игрок получает новый ID. Основной/запасной
статус редактируется отдельно. Запись и аудит выполняются одной транзакцией.

Для обновления существующего сайта: сначала применить `0010`, затем выкатить
приложение с явными публичными выборками игроков, затем применить `0011`.
`0011` запрещает `players.*` для публичных ролей: прежнее приложение ещё использует
эту выборку. После обновления выполнить `npm run db:check`.

### Аккаунты, команды и заявки

На главной есть «Создать аккаунт», в шапке — «Кабинет». Основной вход — Telegram,
без email и пароля. Регистрация запрашивает ник, Telegram-контакт и Steam;
MMR Dota 2, Elo CS2, Faceit и Dotabuff необязательны. Форма сохраняется в
зашифрованной HttpOnly cookie при переходе в Telegram и возвращается в тот же
браузер и домен. `/auth/callback` проверяет одноразовый код/PKCE и Supabase Auth,
а профиль создаёт server action после проверки всех обязательных полей.

Игрок создаёт аккаунт. Капитан создаёт постоянную команду, выбирает турнир,
собирает состав и подаёт командную заявку. Права капитана не занимают игровой слот:
для этого есть «Занять слот самому». Персональные приглашения и ссылки требуют
согласия игрока, действуют 7 дней; членство и вместимость проверяются транзакционно.
Второй капитан и передача управления обычным капитаном также требуют согласия.

«Хочу участвовать» — отдельное необязательное пожелание игрока без команды.
Оно не создаёт турнирную заявку и не занимает место. Организатор видит желающих
в `/admin/t/<slug>/registrations`, все аккаунты — в `/admin/players`. Там можно
открыть контакт/Steam, заметить точный дубль Steam, напрямую добавить или переместить
игрока. Подтверждения при действиях организатора не требуются.

Приём открывается и закрывается вручную в настройках турнира. Число команд не
ограничено; размеры основного/запасного состава настраиваются отдельно.
Принятие заявки создаёт публичный турнирный снимок. Изменение профиля или капитана
не переписывает принятый состав и архив. Контакты и внешние ссылки видят только
сам игрок и организатор; поиск капитанов возвращает ник/код/рейтинги.

Для настройки Telegram используются команды (Node.js 22+, как в CI):

```bash
npm run auth:telegram:check    # только чтение настроек и проверка redirect
npm run auth:telegram:setup    # создать/обновить custom:telegram и callback
```

Для них нужны ключи Supabase из `.env`, `SUPABASE_ACCESS_TOKEN` и
`NEXT_PUBLIC_SITE_URL` с фактическим адресом приложения. Для `setup` также нужны
`TELEGRAM_CLIENT_ID` и `TELEGRAM_CLIENT_SECRET` из BotFather → бот → Login Widget.
В мини-приложении BotFather в Redirect URLs указать
`https://<project-ref>.supabase.co/auth/v1/callback`.
Эти секреты нужны локальному инструменту настройки, в браузер они не попадают.
Команда `setup` сохраняет остальные разрешённые адреса возврата Supabase.
`AUTH_SITE_URL=https://g4z-cup.ru` задаёт основной адрес Supabase Auth,
`AUTH_REDIRECT_ORIGINS=https://g4z-cup.ru,https://g4z-cup-site.vercel.app` добавляет
точные `/auth/callback` обоих доменов. Локальный `NEXT_PUBLIC_SITE_URL` может оставаться
`http://localhost:3000`. Вход всегда возвращается на разрешённый исходный домен:
cookies `.ru` и `.vercel.app` не смешиваются. Восстановление потока в другом
браузере невозможно без исходного PKCE verifier; интерфейс предлагает повторить вход.

Провайдер запрашивает только `openid profile`, без телефона и разрешения писать
пользователю; включён PKCE, `skip_nonce_check=false`, email необязателен.
В реальном redirect проверяются code flow, state и PKCE S256. Supabase не
добавляет nonce автоматически в этот запрос; прежнее требование nonce в preflight
исправлено. Наличие флага `skip_nonce_check=false` само по себе не доказывает
проверку nonce в callback.
Документация: [Telegram OIDC](https://core.telegram.org/bots/telegram-login),
[Supabase Custom Providers](https://supabase.com/docs/guides/auth/custom-oauth-providers).
Сессия игрока отдельна от cookie организатора и никогда не выдаёт административные
права. Proxy обновляет её только на персональных маршрутах; публичные страницы
сохраняют общий кэш. Каждый action проверяет сессию/полномочия и ограничения частоты
независимо от proxy. `/admin/telegram` остаётся закрытой технической проверкой.

Для существующего проекта с миграцией `0010` подготовлен инструмент выкатки:

```bash
node scripts/release-registration.mjs --inspect
node scripts/release-registration.mjs --validate  # вся транзакция откатывается
node scripts/release-registration.mjs --apply     # 0011–0014 и история миграций
npm run db:check
# После выкатки приложения:
node scripts/release-registration.mjs --launch-cup13
```

Запуск CUP 13 идемпотентен: создаёт `g4z-cup-13` по Dota 2, открывает приём,
делает кубок текущим; при повторе не переписывает изменённые организатором настройки.
Даты, призы и матчи не выдумываются. `/api/health` сообщает версию регистрации и
наличие серверных настроек без раскрытия секретов.

Браузерные тесты используют настоящие PostgreSQL-функции в временной PGlite и
изолированный Auth. Проверяются сохранение формы, cookie/PKCE, состав, приглашения,
модерация, права и приватность. Сам Telegram и Client Secret требуют настоящего
входа на рабочем домене; тестовая авторизация не выдаётся за такой вход.

SQL-проверки можно запускать локально без Docker и без доступа к рабочей базе:

```bash
npm run test:db
```

Команда поднимает отдельный PostgreSQL в памяти через PGlite, применяет миграции,
сид/архив и тот же `supabase/tests/logic.sql`, который CI выполняет в PostgreSQL 16.
Проверяется в том числе запрет доступа на заполненных данных для `anon` и
`authenticated`, разрешение для `service_role`, откат сохранения и конфликт версий.

## Деплой

### Проверки

```bash
npm run lint
npm run typecheck
npm test
npm run test:e2e
```

Единственная версия приложения проверяется общей командой `npm run test:e2e`.
Она поднимает изолированные тестовые данные на `127.0.0.1:54329`, собирает
production-приложение и запускает его на `127.0.0.1:3000`. Ключи и сессии тестовые,
настройки Supabase из `.env` переопределяются. Проверяются авторизация, главная,
публичные страницы и админка на 1440/390 px, длинные названия, обе сетки,
отключение движения, разные дисциплины и обновление счёта у зрителя.
Скриншоты сохраняются в `test-results/`. Эти проверки не заменяют SQL-тесты
триггеров, которые CI запускает в отдельном PostgreSQL.

Для проверки preview можно задать `PLAYWRIGHT_BASE_URL`: тогда выполняются
только общие проверки страниц и доступа, без тестов записи и тестовых сессий
организатора.

Главная `/` теперь постоянно показывает сообщество и все активные турниры.
`is_current` выделяет главный кубок. Общие Telegram/эфир берутся из действующих
адресов G4Z CUP; при необходимости их можно переопределить через
`NEXT_PUBLIC_COMMUNITY_TELEGRAM_URL` и `NEXT_PUBLIC_COMMUNITY_STREAM_URL`.

### Публикация приложения

**Порядок важен: сначала база, потом приложение.** Публичные страницы
предрендерятся во время сборки, поэтому если в проекте Supabase ещё нет таблиц и
вьюх, билд упадёт на пререндере `/archive` с сообщением вида
`Could not find the table 'public.tournament_summaries'`.

1. **Применить миграции** к проекту Supabase. Проще всего — открыть
   `supabase/setup.sql` (это все миграции одним файлом), вставить целиком
   в Supabase → SQL Editor и выполнить. Через CLI то же самое делает
   `supabase db push`.
2. **Залить архив** (по желанию, но иначе сайт будет пустым):
   `supabase/data/g4z-cup-10.sql`.
3. **Проверить готовность** перед деплоем:

   ```bash
   npm run db:check
   ```

   Скрипт проходит публичным ключом по всем таблицам и вьюхам, которые запрашивает
   сайт, и печатает, какой миграции не хватает. Он же проверяет обратное: что
   `audit_log` и `login_attempts` анонимным ключом **не** читаются.

4. **Задать переменные окружения** в Vercel (все шесть из таблицы выше, для
   Production и Preview) и запустить деплой.

Сборка намеренно падает, а не отдаёт пустые страницы: при включённых Cache
Components пустой результат попал бы в предрендер и раздавался бы из кэша, то
есть сайт бы «работал», показывая, что матчей нет. Лучше сломанный деплой, чем
пустое расписание во время турнира.

## Как это работает

### Кэш вместо запросов на каждый заход

Все публичные чтения в `lib/queries/public.ts` — это `use cache`-функции с
тегами (`lib/cache/tags.ts`). Страницы попадают в предрендер, Supabase к ним не
привлекается. Любая правка в админке вызывает `updateTag` (`lib/actions/*`), и
затронутые страницы пересобираются: организатор видит свой счёт сразу, зритель
получает статику.

Первая версия сайта стояла на `export const dynamic = "force-dynamic"` на всех
страницах; в Next 16 с Cache Components этой опции больше нет.

### Счёт и сетку считает база

`matches.score1/score2/status/winner_id` **никем не записываются вручную** —
триггер `recalc_match` пересчитывает их по победителям карт, а `advance_bracket`
переносит победителя и проигравшего в следующий матч по `winner_to_match_id` /
`loser_to_match_id`. Удалили карту по ошибке — серия открывается заново, а слот
в следующем матче очищается. Ручную правку слота триггер при этом не перетирает.

Отсюда же следует, что сетка на сайте рисуется по связям матчей, а не парсингом
названий раундов.

### Генератор сеток

`lib/brackets/` — чистые функции без обращений к базе, покрытые юнит-тестами:

- круговая система (метод круга, при нечётном числе команд одна отдыхает);
- швейцарка: первый тур по посеву, дальше пары по результатам с избеганием
  повторов (с откатом при тупике);
- single elimination с корректными байями и матчем за 3 место;
- double elimination: верхняя и нижняя сетки, гранд-финал, `2n − 2` матчей.

Из админки (`/admin/t/<slug>/structure`) весь этап создаётся одной кнопкой:
матчи, время туров и связи продвижения.

### Ведение матча

`/admin/t/<slug>/live` — экран под телефон: по одному тапу на карту, «отменить
карту» рядом, старт матча из очереди. Всё остальное (счёт серии, статус,
продвижение) считает база. Зрительские страницы обновляются через Supabase
Realtime (`components/live/LiveRefresher.tsx`), с медленным поллингом как
резервом.

### Авторизация

Один общий пароль организаторов, но:

- пароль хранится scrypt-хэшем в переменной окружения;
- сессия — cookie, подписанная HMAC-SHA256, с истечением через 12 часов
  (`lib/auth/session.ts`), а не строка вида `authorized`;
- перебор ограничен: 8 неудачных попыток с одного IP за 15 минут
  (таблица `login_attempts`);
- каждая правка пишется в `audit_log` и видна на `/admin/audit`.

`proxy.ts` (в Next 16 это бывший middleware) — оптимистичный шлюз, который не
пускает браузер в админку. Настоящая проверка — `assertAdmin()` внутри **каждого**
server action, потому что action доступен прямым POST-запросом.

### Права в базе

RLS включена на всех таблицах. Публичной роли выдан только `select`, и только по
опубликованным турнирам — черновик следующего сезона можно готовить на живом
сайте. Политик на запись нет вообще: писать может лишь service-role ключ, который
живёт в серверных переменных окружения. `login_attempts` и `audit_log`
недоступны публичной роли даже на чтение.

## Ввод прошедшего турнира руками

Если старой базы уже нет (или турнир вообще был до этого сайта), заводить всё
через сетку не нужно. `/admin/t/<slug>/history` — три шага:

1. **Команды списком** — вставить названия по одному в строке, адреса страниц
   построятся сами, дубликаты пропустятся.
2. **Сыгранный матч** — выбрать две команды и ввести счёт серии (`2:1`).
   Формат серии определяется по счёту (2 победы → bo3), и карты под этот счёт
   создаются автоматически: счёт в базе по-прежнему считается по картам, просто
   вводить их по одной не приходится. Название матча можно взять из подсказок —
   «Финал», «Матч за 3 место», «Полуфинал».
3. **Итоговые места** — кнопка «Заполнить по результатам» разберёт финал и матч
   за 3 место и проставит топ-4. Дальше места и награды (MVP) правятся вручную
   на вкладке «Итоги».

Минимум для исторической записи — это финал и матч за 3 место: топ-4 после них
заполняется одной кнопкой.

## Перенос истории G4Z CUP 10

1. Применить архивную запись: `psql "$DATABASE_URL" -f supabase/data/g4z-cup-10.sql`
   (турнир, семь команд, итоговые места и MVP).
2. Перенести матчи, карты, драфты и составы из старого проекта Supabase:

```bash
OLD_SUPABASE_URL=... OLD_SUPABASE_KEY=... \
NEXT_PUBLIC_SUPABASE_URL=... SUPABASE_SERVICE_ROLE_KEY=... \
node scripts/import-legacy.mjs --dry-run
```

Скрипт читает схему первой версии (`matches`, `match_games`,
`match_game_picks`, `match_game_bans`), сопоставляет команды по названию и
переносит всё в новую структуру. Счёт и статусы пересчитает база. Без
`--dry-run` матчи турнира заменяются целиком, так что скрипт можно запускать
повторно.

Если старого проекта Supabase уже не существует, этот шаг пропускается —
результаты вносятся вручную, см. раздел выше.
