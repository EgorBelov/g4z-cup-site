# G4Z CUP: план редизайна «Орбита» и регистрации игроков

Статус на 11 ноября 2026: дизайн «Орбита» реализован в основном приложении, идёт итоговая проверка первого этапа. Продуктовые решения по регистрации согласованы; второй этап ещё не реализован. Этот документ хранит согласованный объём и фактический прогресс.

### Текущее состояние реализации

- Одна основная версия приложения: новый дизайн заменяет прежний на существующих маршрутах. Отдельного приложения, переключателя версий и специальной команды проверки редизайна нет; все браузерные проверки входят в `npm run test:e2e`.
- Реализованы: токены «Орбиты», SVG-логотип и иконка, анимация с отключением и `prefers-reduced-motion`, постоянная главная, архив, публичные турнирные страницы, административные и служебные экраны, мобильная навигация и ведение матча.
- Визуальное уточнение от 11 ноября: вместо текстовых рядов — карточки с фоном, обложками, иконками и отдельными плашками статистики. На главной и в архиве добавлены фильтры дисциплин; на обзоре турнира — плитки разделов. У карточек есть реакции на наведение и фокус, движение учитывает `prefers-reduced-motion`.
- Контуры логотипа восстановлены по верхнему знаку из `work/logo.jpg`; встроенный компонент использует `public/brand/g4z-cup.svg` как единый источник. Визуально проверены размеры 560 и 44 px.
- Сохранены BO2/ничьи, обе сетки и несколько этапов. MMR и Dota-драфты скрыты для других дисциплин; средний MMR считает основные слоты и показывает заполненность.
- Проверки запускают production-сборку с изолированными заполненными данными на 1440/390 px: доступ, страницы, навигация, движение, обе сетки и обновление счёта у другого зрителя. SQL-логика проверяется в отдельном PostgreSQL в CI.
- Миграция `0009_match_lifecycle.sql` применена в рабочем Supabase: команды старта/отмены/возобновления выполняются в БД, приложение не пишет вычисляемые поля матча. Добавлены SQL-ассерты и проверка доступности/прав функции в `db:check`; проверка рабочей базы прошла. Сверены и зарегистрированы в истории ранее применённые вручную `0007/0008`.
- Подключение к Supabase проверено по `.env`: существующие таблицы/вьюхи доступны, операционные таблицы закрыты для публичного ключа; два видимых турнира завершены.
- Следующий этап: проверка Telegram OIDC/Supabase Auth и реализация регистрации, постоянных команд, заявок и модерации по разделам 3–7. До связи с аккаунтами исправить сопоставление игроков состава по позиции на устойчивые ID.

## 3. Вход, профиль и приватность

### 3.1. Единая регистрация и вход через Telegram

- Единственный вход — Telegram. Discord и интерфейсы привязки второго способа входа исключены из текущего объёма.
- При регистрации человек указывает в одной форме три обязательных поля: публичный ник, Telegram `@username` для связи и ссылку на Steam. MMR, Elo, Faceit и Dotabuff необязательны и могут быть добавлены позднее в профиле.
- Подтверждение Telegram-аккаунта — часть этой же регистрации. Не вводить отдельный пользовательский этап «первое заполнение профиля» после успешной регистрации. Регистрация завершается только после подтверждения аккаунта и валидации всех трёх обязательных полей.
- Возвращающийся пользователь входит в существующий аккаунт без повторного ввода этих полей. Ошибки или незавершённое подтверждение оставляют пользователя в сценарии регистрации, а не отправляют в отдельное заполнение профиля.
- Telegram ID — стабильный идентификатор аккаунта; публичное имя, ник сайта и `@username` — разные поля. Повторный вход с тем же ID открывает тот же профиль, смена username не создаёт нового игрока.
- Использовать доступные данные подтверждённого входа для заполнения контакта; ручной ввод проверять по формату, но не выдавать за доказанное владение. Обновление контакта не перепривязывает Telegram ID.
- Телефон не запрашивать. Организатор видит доступный Telegram-контакт и может перейти к нему. Само наличие username не гарантирует доставку сообщения.
- Сессия игрока отдельна от административной cookie и не даёт доступа в `/admin`.

### 3.2. Показатели уровня и дополнительные ссылки

- В профиле необязательные показатели по дисциплинам: Dota 2 — MMR, CS2 — Elo. Не превращать их в одно общее поле «уровень игрока» и не считать рейтинг обязательным.
- Модель позволяет добавлять показатели других дисциплин. Конкретный источник Elo CS2 не объявлять подтверждённым автоматически; рейтинг заявлен пользователем, как и MMR.
- Faceit и Dotabuff — необязательные ссылки профиля. Steam, Faceit и Dotabuff проверять по формату/домену; это не подтверждает владение внешним аккаунтом.
- Точный нормализованный дубль Steam у разных профилей подсвечивать организатору для ручной проверки. Не отказывать автоматически и не обещать надёжное выявление одного человека по разным URL.
- На турнирной странице команды показывать имеющийся показатель для её дисциплины. Для другой дисциплины не подписывать число как MMR и не подставлять вместо отсутствующего значения 0.
- При необходимости среднего использовать только основные слоты и одинаковый показатель/дисциплину. Если значения есть не у всех, указать заполненность, не выдавая частичную выборку за среднее всего состава; запасные отдельно.
- Автоматических порогов допуска, требования рейтинга или скриншота нет. Участие подтверждает организатор.

### 3.3. Видимость

- Ник и необязательные игровые показатели публичны в опубликованных составах и разрешённой поисковой выдаче. Командные страницы показывают заполненные значения.
- Telegram, Steam, Faceit и Dotabuff видят только сам игрок и организаторы; другие игроки/капитаны не получают эти данные через состав, поиск, общий кэш или Realtime.
- Публичный каталог всех одиночных игроков и отдельная публичная страница профиля в текущем объёме не нужны. Организатор видит игроков без команды, капитан пользуется ограниченным поиском.
- На форме явно объяснить публичность ника/показателей и доступ организаторов к контактам/ссылкам для связи и модерации.
- Изменение профиля не переписывает принятые составы и архив. Для заявки хранить версию значимых данных, которую рассматривал организатор.

## 4. Постоянные команды и капитаны

- Каждый зарегистрированный игрок может создать постоянную команду и становится главным капитаном; обязательные поля уже указаны при регистрации.
- У команды один главный капитан и один необязательный второй капитан. Оба ведут заявки, приглашают участников и меняют незаблокированные составы.
- Передача основного управления, назначение/снятие второго капитана и закрытие команды — полномочия главного капитана. Второй не отбирает управление у главного и не закрывает команду.
- Обычная передача главного капитанства требует подтверждения получателя; запрос действует 7 дней и может быть отозван. До принятия полномочия остаются у прежнего капитана.
- Назначение второго капитана обычным пользователем также требует согласия получателя; главным и вторым не может быть один человек. Получатель — зарегистрированный игрок.
- Если главный капитан пропускает/не ведёт следующий кубок, он передаёт капитанство либо назначает второго. Отдельную роль неиграющего менеджера и независимого «игрового капитана без полномочий» не вводить.
- Полномочия постоянной команды и факт участия в конкретном составе хранить отдельно; права капитана не занимают игровой слот автоматически.
- Организатор назначает/снимает обоих капитанов и передаёт управление напрямую, без подтверждения получателя. Изменения аудируются, исторические капитаны/составы не переписываются.
- Постоянная команда имеет публичную страницу сразу после создания: название, тег, описание, капитаны и история участий; черновые составы и контакты скрыты.
- Уникальный адрес — постоянный идентификатор команды. Для похожих названий показывать тег/адрес; не использовать название как ключ БД.
- Закрытие — архивирование без удаления матчей, составов, драфтов и наград. Закрытая команда не создаёт заявки/приглашения и не входит в активный поиск.
- Самостоятельное закрытие: сначала отозвать непринятые заявки; если есть принятое участие в незавершённом турнире, требуется решение организатора. Не снимать команду с турнира автоматически.
- Восстановление закрытой команды — организатором; адрес не освобождается для новой команды.

## 5. Турнирные заявки и составы

### 5.1. Приём заявок

- Количество команд без автоматического лимита. Обязательные даты открытия/закрытия и автоматическое завершение приёма не вводить: допуск контролирует организатор вручную.
- Для управления оставить ручное открытие/закрытие приёма у турнира. Пока приём открыт, заявки можно создавать и подавать без числовой вместимости/автоматического дедлайна. Это трактовка пожелания о неограниченном приёме; настройка не должна автоматически закрывать турнир по числу команд.
- Закрытие приёма ограничивает самостоятельную подачу/редактирование/вступление, но не останавливает модерацию уже поступивших заявок. Организатор может открыть приём снова и управляет заявками независимо от этого переключателя.
- Аккаунты и постоянные команды можно создавать вне приёма конкретного турнира.
- Черновики и приглашения не являются принятыми участниками. В турнирные команды, группы и посев попадают только принятые заявки.

### 5.2. Состав

- Размер состава настраивается организатором отдельно для каждого турнира: число основных и максимум запасных. Стандарт для Dota 2/CS2 — 5 основных + до 2 запасных; другие дисциплины не обязаны играть пятёрками.
- Для подачи нужны требуемое число основных и не более разрешённого числа запасных. Обычные участники состава уже зарегистрированы с обязательными данными; игровой рейтинг не требуется.
- Главный/второй капитан назначает основных и запасных до подачи. Вступление нового игрока не вытесняет основного автоматически.
- Один игрок занимает место только в одной действующей заявке конкретного турнира, включая запасных. В разных кубках может выступать за разные команды.
- Для обычных пользователей место занимает подтверждённое вступление; приглашение ничего не резервирует. Организатор может добавить участника напрямую.
- До принятия заявки, пока приём открыт, игрок может выйти, капитан — исключить его или сменить основной/запасной статус. После принятия либо закрытия приёма изменения проводит организатор.
- Отказ/лист ожидания сами по себе не освобождают состав. До принятия участник может выйти либо капитан отзывает заявку; отзыв освобождает членство для другой заявки этого турнира, сохраняя историю.

### 5.3. Состояния заявки

- Одна заявка постоянной команды на конкретный турнир; повторная подача — версия той же заявки, без дублей.
- Состояния: черновик → на проверке → принята / отклонена / лист ожидания; отдельно отозвана.
- Причина отказа обязательна, доступна участникам заявки и организаторам, публично скрыта.
- Исправить отказ и подать снова можно, пока приём открыт. Лист ожидания — ручной статус организатора, без автоматической очереди и резервирования мест.
- Изменение поданной/ожидающей заявки обычным пользователем возвращает её в черновик и требует повторной подачи. Изменение значимых данных профиля до принятия обновляет состояние только затронутых заявок/дисциплин; организатор не принимает устаревшую версию.
- При принятии публикуются турнирная команда и снимок состава/значимых данных. Состав блокируется для самостоятельных изменений.
- До принятия и при открытом приёме капитан может отозвать заявку. Повторная подача отозванной требует заново проверить свободное участие и собрать подтверждения; старое членство не восстанавливается автоматически.
- После принятия отзыв, снятие с турнира и замены — через организатора. Если уже есть посев/матчи, не удалять турнирную команду автоматически и не править вычисляемый счёт/статус из приложения.

## 6. Приглашения, поиск и полномочия организатора

### 6.1. Обычные приглашения

- Два способа: персонально через поиск зарегистрированного игрока по нику или по ссылке в состав конкретной турнирной заявки.
- Игрок сам принимает/отклоняет обычное приглашение. Перед согласием показывать команду и турнир. Незарегистрированный игрок проходит единую регистрацию, возвращающийся — вход; затем вернуть к приглашению.
- Срок персонального приглашения/ссылки — 7 дней. Капитан может отозвать; новую ссылку выпускать с отключением прежней.
- Ссылка многоразовая до заполнения допустимого состава. При одновременных принятиях число мест проверяется атомарно; повторное принятие одним игроком не создаёт дубль.
- Обычное вступление блокируется при закрытом приёме, принятой/отозванной заявке, истёкшем/отозванном приглашении, занятом составе или участии в другой заявке того же турнира.
- Повторное открытие приёма не продлевает срок ссылки автоматически.
- Поиск доступен вошедшему капитану/второму капитану: публичный ник, короткий постоянный код игрока и заполненные игровые показатели с обозначением дисциплины. Ник может повторяться; контакты/внешние ссылки скрыты.

### 6.2. Организатор

- Организатор управляет турнирными данными, заявками, составами и капитанами напрямую. Его изменения **не требуют подтверждений игроков или капитанов**.
- Добавление/замена/перемещение участника, смена роли, передача управления и принятие заявки не создают ожидания пользовательского согласия, если действие выполняет организатор.
- Не вводить отдельные предложения замены с подтверждением новым игроком для административных действий. Обычные пользовательские приглашения по-прежнему требуют согласия.
- Административные изменения обходят пользовательскую блокировку состава/закрытый приём. Причины решений и существенные изменения фиксируются в журнале и видны в кабинете затронутым участникам.
- Полные полномочия относятся к управлению данными, а не к нарушению целостности БД: сохранять ссылки/историю, серверную валидацию, уникальное действующее участие в турнире и расчёт исходов матчей триггерами. При перемещении игрока между заявками обновлять обе стороны одной операцией.
- Ручной ввод старых турниров и составов без Auth-аккаунтов сохраняется, не требует задним числом регистрации/подтверждений.

### 6.3. Кабинет и уведомления

- В кабинете: входящие приглашения, запросы капитанства, участия команды, текущие составы, статусы/причины решений и административные изменения.
- Контакты/Steam не становятся видимыми другим членам команды через уведомления.
- Автоматические личные сообщения и уведомления Telegram-ботом в релиз не входят.
- На старте ограничения частоты действий по аккаунту/IP; капчу добавлять при подтверждённой необходимости, не считать условием выпуска.
- Утрата Telegram-аккаунта — ручное обращение к организатору и проверка личности. Автоматического восстановления по нику/Steam-ссылке нет.

## 7. Техническая основа и изменения данных

### Что уже есть и что сохраняем

- `teams`/`players` — турнирные команды/составы. На игроков ссылаются пики/награды. Не превращать эти таблицы в постоянные команды или глобальные аккаунты; сохранять существующие идентификаторы.
- `players.mmr` уже необязателен и означает заявленный MMR на момент турнира. При расширении не трактовать старый MMR как CS2 Elo и не заполнять отсутствующие рейтинги фиктивными значениями.
- Сейчас `tournaments.game` — текст; ввести устойчивое обозначение дисциплины и совместимое сопоставление существующих значений. Не полагаться на произвольную строку при выборе поля рейтинга/игрового UI.
- Драфты героев и роли Dota показывать только для соответствующей дисциплины. CS2/другие игры не получают Dota-специфичные поля по умолчанию. Автоматический импорт игровой статистики не входит в задачу.
- `saveRosterAction` сопоставляет игроков по позиции строки. До связи с аккаунтами перейти на устойчивые ID, чтобы перестановка не меняла личность в драфтах/наградах.
- `LiveRefresher` вызывает `router.refresh()` по событиям БД/таймеру. В первом релизе сохранить и проверить этот механизм; независимый live-блок не является обязательной переделкой.
- `BracketView` уже поддерживает верхнюю/нижнюю сетки и финалы. Новый дизайн сохраняет их и учитывает несколько этапов; мобильное представление проверить на заполненных данных.
- `setMatchStatusAction` использует `set_match_lifecycle` из миграции `0009`; функция проверяет старт/отмену/возобновление и вызывает `recalc_match`. Счёт и завершение серии по-прежнему считаются из карт. Перед выкаткой приложения применить миграцию и выполнить `db:check`.

### Предлагаемая схема (названия новых таблиц рабочие)

- `player_profiles`: Auth ID, стабильный Telegram ID, обязательные ник/Telegram username/Steam, статус проверки контакта и необязательные Faceit/Dotabuff. Создавать полноценный профиль при завершении единой регистрации. Временное техническое состояние OAuth/формы не считать зарегистрированным игроком и не показывать как отдельный этап заполнения профиля.
- Справочник дисциплин/показателей и `player_ratings`: профиль, дисциплина, тип показателя, необязательное заявленное значение. Для старта Dota 2 MMR и CS2 Elo, без обязательности и смешивания шкал.
- `community_teams`: постоянная команда, главный капитан, необязательный второй, адрес/описание и состояние закрытия.
- Запросы назначения/передачи капитанства: инициатор, получатель, тип роли, срок/отзыв/состояние. Подтверждение только для действий обычного капитана, административные изменения прямые.
- `registration_teams`: постоянная команда, турнир, состояние/версия заявки, причина решения и связь с опубликованной турнирной командой.
- `team_members`: участие профиля в заявке конкретного турнира, основной/запасной, состояние действующего членства. Уникальность участия в пределах турнира, а не всей истории.
- `team_invites`: персональное приглашение или хэш токена ссылки, заявка, срок и отзыв; подтверждение создаёт членство только после всех проверок.
- Существующие `teams`/`players` — публичные турнирные снимки, с необязательными связями с постоянной командой/профилем для совместимости архива. Снимки рейтингов — по дисциплине/типу, отдельно от текущих значений профиля.
- В турнире: ручное состояние приёма заявок, число основных и максимум запасных, дисциплина. Автоматические лимиты команд/обязательные дедлайны не вводить.
- В аудит добавить идентификатор/тип действующего лица; сейчас журнал содержит действие/IP без связи с аккаунтом.
- Любые изменения — только новыми миграциями со следующего свободного номера (на момент анализа `0009`), старые миграции не редактировать.

### Запись, чтение и транзакции

- Публичные чтения через `lib/queries/public.ts`, `use cache` и теги `lib/cache/tags.ts`. Каждая мутация инвалидирует затронутые публичные теги через `updateTag`; персональные данные не попадут в общий кэш.
- Административные actions начинаются с `assertAdmin()`. До добавления действий игроков дополнить `AGENTS.md`: пользовательские actions начинают с отдельной проверки сессии/полномочий, не ослабляя административную защиту.
- Формы через схемы `lib/validation/schemas.ts` и `parseForm`; запись service role через `lib/supabase/write.ts` в server actions; write-модули `server-only`.
- У игроков нет политик прямой записи. Service role обходит RLS, поэтому ownership/роль проверяется на сервере для каждого действия, без доверия скрытым полям формы.
- Принятие приглашения, принятие заявки, перенос игрока, административная замена и передача капитанства — атомарные операции с повторной проверкой текущего состояния. Не создавать дубли при повторах/конкурентных запросах.
- Миграция `0006` выдаёт SELECT новым таблицам по умолчанию, текущие публичные запросы выбирают `players.*`. Для приватных таблиц/полей нужны явные GRANT/REVOKE/RLS и проверка всех вьюх/прав вызова функций, а не только скрытие UI.
- `audit_log`/`login_attempts` остаются недоступны публичной роли. Приватность проверить также для чужого вошедшего игрока, капитана и Realtime.
- Вычисляемые `matches.score1/score2/status/winner_id/loser_id` из приложения не записывать. Исходы серий/продвижение остаются у триггеров.
- Время в часовом поясе турнира; `datetime-local` через `toDateTimeLocal`/`fromDateTimeLocal`.

### Telegram Auth — техническая проверка перед реализацией

- Проверить Telegram OIDC + Supabase Custom OAuth/OIDC Provider в тестовом окружении: вход без email, отсутствие отдельного Telegram UserInfo endpoint, callback/PKCE, сессия, повторный вход в тот же профиль и контакт.
- Использовать Auth-аккаунт Supabase, без параллельной самодельной Telegram-сессии. Отдельная подписанная cookie организатора сохраняется.
- Добавить безопасный возврат после единой регистрации или входа к приглашению и обновление сессии с учётом Cache Components. Сохранить введённые регистрационные данные при переходе к Telegram и возврате с callback, не помещая приватные поля в URL или общий кэш.
- Перед кодом читать руководства установленной версии Next.js в `node_modules/next/dist/docs/`; зависимости установлены, приложение использует Next.js 16.2.1.
- Источники: [Telegram Login/OIDC](https://core.telegram.org/bots/telegram-login), [Telegram username](https://telegram.org/faq#q-do-i-need-a-username), [Supabase Custom OAuth/OIDC Providers](https://supabase.com/docs/guides/auth/custom-oauth-providers). Наличие OIDC в документации не заменяет проверку совместимости выбранной конфигурации.
